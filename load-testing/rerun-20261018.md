# DpCon fresh local scalability run

**Run date:** 2026-10-18, local time (Asia/Kolkata)  
**Target:** `http://127.0.0.1:8080`  
**Database:** local H2 file database  
**Load generator:** Locust 2.44.1, Python 3.11  
**Workload:** authenticated inventory and score reads, occasional passport exports and consent add/withdraw actions; 1–3 seconds of simulated user think time. Each run lasted 2 minutes including ramp-up.

## First visible scalability gap

Inventory reads slowed the most as concurrency increased. Their p95 was 12, 15, 33, and 60 ms at 20, 40, 80, and 160 users. Average inventory response size also grew from about 47 KB to 343 KB across these runs. The workload repeatedly adds and withdraws shares for its test account, and withdrawal keeps a record in the inventory, so this specifically exposes the cost of returning a growing full history. The current endpoint has no pagination.

The stress run sustained 160 concurrent users without HTTP failures, so this run did not find a hard failure threshold. It does show response-time and payload growth that should be addressed before testing larger real customer histories. A useful next test is a seeded account with thousands of consent rows, followed by a paginated inventory implementation and a repeat run.

## Scope and limits

- Each Locust run creates one disposable account outside measured statistics, shares that account across its virtual users, and deletes it after the run. Cleanup completed successfully; the failure and exception CSVs are empty.
- The backend used local H2, not the PostgreSQL Compose deployment. No CPU, heap, GC, connection-pool, or disk metrics were collected.
- AI policy analysis was excluded because the local AI service is configured for automatic provider fallback and could call an external model provider.
- These are measurements of this local machine and workload, not a production capacity guarantee.
